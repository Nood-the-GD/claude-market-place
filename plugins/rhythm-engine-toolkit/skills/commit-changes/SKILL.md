# Committing Code Cleanly — Rhythm Engine

The working tree in this project mixes real source changes with Unity Editor
noise: reimport touches, ad-SDK version bumps, local dev toggles, Play-mode
save-state. Never `git add -A` / `git add .` here — always stage explicit
paths per commit.

Classify every path `git status` reports, not just the files touched or
discussed earlier in the current conversation. A file's presence or absence
from the session's own edits is not a classification signal — a pending
change from an earlier session, another tool, or a teammate's stash-pop is
exactly as eligible as one made this turn. Decide purely from what `git diff
-- <path>` shows against the rules below.

**Default posture: commit it.** The bar here is not "prove this file is
related" — it's "this isn't generated noise, and committing it won't
silently change logic, delete something, or leave a referenced file
missing." Exclusion is for the specific noise patterns below, not a general
caution reflex.

## Always commit

- **C# files.** Always in scope — they're the source of truth for intent.
- **Pure renames/moves** — path or name changed, content (and for a paired
  `.meta`, the GUID) unchanged. In this repo a Unity rename often shows up
  as *one tracked delete + one untracked add* with a different name (Unity
  identity lives in the `.meta` GUID, not the path), which `git status -uno`
  cannot see — see the untracked-file check in Process step 1. Confirm it's
  actually a pure rename (diff the old and new file contents, or trust
  git's own rename detection once staged) before treating it as one; a
  same-looking rename that also changed a serialized value is not pure.
- **A newly added package** — a new entry in `Packages/manifest.json` /
  `packages-lock.json`, or a new package folder. Ship it with whatever C#
  change needed it.
- **Everything else, once it's not generated noise (below).** Prefab /
  scene / material / shader / asset changes that trace to a modified C#
  file in the same commit (a component added/removed, a serialized field
  newly wired to a script member, a GUID/string matching a renamed C#
  constant, a database asset's entry added/renamed to match a paired C#
  diff) are the clearest case, but the point of "default: commit it" is
  that a plausible, undramatic asset change doesn't need a proven C# link
  to be included — it needs to not be one of the noise patterns below, and
  you need to have actually looked at its diff rather than guessed from the
  filename.

## Always leave out: generated / local-only noise

Recurring noise patterns in this repo's working tree:

- Runtime/save-state ScriptableObjects: `ModuleUserData/**/*.asset`
  (`UserData*.asset`) — generated by Play-mode/test runs, not authored.
- Ad-SDK / mediation config: `LevelPlay/**`, `GDKSymbolDefine.asset` —
  generated by the SDK's own version/symbol updater.
- Addressables build output: `AddressableAssetsData/link.xml(.meta)`.
- Editor tool state: `vInspector Data.asset` — generated by the tool.
- A lone local dev/remote-config toggle with nothing in a modified C# file
  that reads it (a `_forceLocalGameDesignConfig` flip in a `.unity` scene,
  an unreferenced `FirebaseConfig.asset` field) — a personal local
  override, not something meant to ship.
- Meta-only diffs on unrelated art (transform numbers, GUID reordering,
  fileID churn) with no corresponding C# change and no rename.

## Process

1. `git status --porcelain=v1 -uno` **and** a plain
   `git status --porcelain=v1 | grep '^??'` for untracked files — never
   `-uall`. The untracked pass exists specifically to catch the other half
   of a Unity rename (see "Always commit" above) and any newly added
   package/asset that a modified file now depends on. Treat the full output
   as the candidate set, including paths never mentioned earlier in the
   conversation — don't pre-filter to "files I already know about."
2. Classify every path with the rules above. For each `.prefab` / `.unity`
   / `.mat` / `.shader` / `.shadergraph` / `.asset` on the fence, run
   `git diff -- <path>` — don't guess from the filename or directory alone.
   When a file is included *because* it references another file (a GUID, a
   database entry pointing at a prefab), resolve that reference and confirm
   the target is itself tracked or staged in the same commit — an asset
   diff that points at an untracked file ships a dangling reference.
3. Group the included files into logical commits: one concern per commit,
   in dependency order (a shared API/schema change lands before the callers
   that use it) so each commit compiles independently. Splitting further
   because two features got mixed together is expected, not a failure to
   avoid.
4. Anything genuinely ambiguous after applying the rules above — not a
   rename, not a package add, not obviously generated, and no clear link to
   a modified C# file — don't silently include or exclude it: list it
   separately. If the user has already said not to ask for this task (e.g.
   "just commit, don't ask"), that instruction holds for the rest of the
   task — resolve it yourself using the closest matching default above
   (generated/noise-like → leave out; otherwise → include) and report the
   call instead of asking again. Only ask mid-task for something the rules
   here genuinely don't cover.
5. Stage each commit's files by explicit path, write a message matching
   this repo's convention (see `git log --oneline`: `type(scope): imperative
   summary`, e.g. `feat(search):`, `fix(search):`, `chore(search):`), then
   commit.
6. Report what was committed in each commit and what was left out (and
   why), so the user can review the exclusions.

## Common mistakes

| Mistake | Fix |
|---|---|
| `git add -A` / `git add .` | Stage explicit paths per commit |
| Treating "no proven C# link" as a reason to exclude a plausible asset change | Default is commit; exclude only for the specific generated/local-only patterns above |
| Missing the other half of a Unity rename because `-uno` hides untracked files | Also check `git status --porcelain=v1 \| grep '^??'` for rename targets and new dependencies |
| Including an asset that references a GUID/path without checking the target is tracked | Resolve the reference and confirm the target is tracked or staged in the same commit |
| Bundling unrelated features into one commit to avoid splitting work | Split — one concern per commit is the point |
| Silently dropping a genuinely ambiguous change with no fitting default | Surface it to the user instead of guessing |
| Asking again mid-task after the user already said not to ask | "Don't ask" holds for the rest of the task — resolve with the closest default and report it |
| Skipping a modified file because it wasn't edited or discussed earlier in the conversation | Classify every path from `git status`, session-touched or not, by its diff content alone |
